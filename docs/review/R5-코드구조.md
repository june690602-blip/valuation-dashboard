## 어떻게 확인했나

**하나 — 구조를 숫자로 못 박았다.** `scripts/check_structure.py`.

```bash
python scripts/check_structure.py          # 전체 (네트워크·키 불필요)
python scripts/check_structure.py --list   # 레지스트리(예산·헬퍼·계산 경계)만
```

여덟 검사다. R4의 `check_design.py`와 같은 레지스트리 방식이다 — **새 파일을 만들거나
헬퍼를 복사하면 등록해야 통과한다.**

| | 검사 | 무엇을 못 박았나 |
|---|---|---|
| A | 파일 크기 | 파일마다 줄 수 상한(`SIZE_BUDGET`). **예산은 내려가기만 한다** |
| B | 중복 헬퍼 | `esc`·`el`·`$` 같은 공용 함수가 몇 벌인지 · 벌끼리 **로직이 갈렸는지 주석만 갈렸는지** |
| C | CSS의 거처 | 공용 파일 대 페이지별 `<style>` 줄 수 비율 |
| D | 인라인 스타일 | 파일별 `style="` 개수(`INLINE_BUDGET`) · 형제 파일과의 밀도 차 |
| E | 계산 경계 | 브라우저에서 도는 금융 수식 전수 등록 · **파이썬 쌍둥이가 있는가 · CI가 어느 쪽을 도는가** |
| F | 직렬화 층위 | `serialize.py`가 값을 옮기는지 만드는지 |
| G | 검증 스크립트 | 정적 스크립트가 CI에 걸려 있는가 · **실패 시 0이 아닌 값을 반환하는가** |
| H | 죽은 코드 | 안 쓰이는 함수·CSS 클래스 · 로컬 시안 |

A의 `SIZE_BUDGET`이 R1의 `PRICE_LEVEL_SITES`·R3의 `LAYER_SITES`·R4의 `SHELL_SITES`와 같은
역할이다. 특히 **예산은 내려가기만 한다**는 규칙이 이 라운드의 산출물을 지킨다 — `stock.js`를
쪼개고 예산을 1,990에서 내려 적으면, 다음 사람이 다시 부풀릴 수 없다.

**둘 — 이식이 실제로 일치하는지 숫자로 대조했다.** `bond.js`의 채권 수학은
`bond_math.py`를 손으로 옮긴 것이다. "코드를 읽어 보니 같다"와 "같은 입력에 같은 값이
나온다"는 다르므로, JS 로직을 파이썬으로 그대로 옮겨 **UI가 만들 수 있는 조합 144개**
(이표 0/3.25/5% × YTM 0.1/3.25/6% × 만기 8종 × 주기 2종)에 대해
지표 5종과 시나리오 6행×4열을 전수 대조했다. → **최대 상대오차 2.6×10⁻¹⁴**(부동소수 잡음).

**셋 — 베이스라인을 먼저 확정했다.** 분할은 **동작 무변경**이어야 하므로, 무엇이 "변하지
않았음"의 기준인지 먼저 재 두었다.

```bash

python -m pyflakes app.py server.py src scripts tests   # 0건
node --check web/assets/*.js           # 6/6 통과
```

**ROE 십자선이 자사 값과 정확히 같다(18.86%).** 표본이 9개(홀수)라 중앙값이 삼성전자 자신이

라벨("저PER · 고ROE")이 대상 종목에 대해서는 뜻을 잃는다 — 자기 기준선 위에 앉아 있으니
위도 아래도 아니다.

편향의 방향도 한쪽이다. 자사를 넣으면 중앙선이 자사 쪽으로 끌려가 **실제보다 업종에 가까워
보인다.** 삼성전자는 PER이 피어보다 비싸고(16.73 vs 11.66) ROE도 높은데(18.86 vs 16.43),
십자선이 둘 다 자사 쪽으로 올라가 **비싼 정도와 잘하는 정도를 동시에 축소해서 보여준다.**

덤으로 **한 화면에 "업종 중앙 PER"이 세 값으로 존재한다** — 표본 정의가 셋이기 때문이다.

| 화면 자리 | 계산하는 곳 | 표본 | 삼성전자 |
|---|---|---|---|
| 업종비교 탭 산점도 십자선 | **브라우저**(`stock.js:602`) | 정제 피어 + PER·ROE 둘 다 있는 행 + **자사 포함** | **12.77×** |

### 2. 이슈로 남김 — 범위가 커서 별도 작업이 필요한 것

#### ㉮ `stock.js` 1,990줄 — 이 라운드의 1순위

이슈 #54가 "예산이 빠듯하면 R5 전체를 버리고 이 분할 하나만 남긴다"고 지목한 것이다.
읽어 보니 **경계는 이미 파일 안에 있다.** 자를 자리를 못 찾는 문제가 아니라, 한 IIFE가
그 경계들을 다 삼키고 있는 문제다.

| 줄 범위 | 무엇이 사는가 | 밖으로 나가는 의존 |
|---|---|---|
| 9–33 | DOM·문자열 빌더 (`ATTR`·`kebab`·`styleStr`·`el`·`esc`·`$`) | 없음 — **그대로 뺄 수 있다** |
| 68–88 | 포맷터 9개 + 판정 어휘 헬퍼 3개(`vIdx`·`vPos`·`vTone`) | 모듈 전역 `CUR` 하나 |
| 95–204 | 값 구동 차트 (`bulletChart`·`radarChart`·`scoreBars`) | 전역 `D` |
| 208–501 | **주가 캔버스 차트 (294줄)** | `makePriceChart(container, D, state)` — **이미 인자로 받는다** |
| 503–667 | SVG 차트 원시 도구 (`bandChart`·`barGroups`·`lineMulti`·`niceStep`·`peerScatter`) | 전역 `D`·`state` |
| 669–789 | 검색·자동완성·상호작용 배선 | 전역 `state`, `load()` |
| 791–865 | WACC·백테스트 차트 | 전역 `D` |
| 867–1475 | **주식 9탭 섹션 렌더 (609줄)** | 전역 `D`·`state` |
| 1477–1846 | **ETF 뷰 (370줄)** | 전역 `D` — **그런데 스키마가 다르다(㉯ 참조)** |
| 1848–1990 | 오케스트레이션 (`renderAll`·`load`·`switchTab`·`init`) | 전부 |

**분할을 막는 것은 빌드 도구가 없다는 사실이 아니다.** 브라우저가 ES 모듈을 그대로
이해하므로(`<script type="module">`) 순수 정적 서빙에서도 `import`/`export`가 된다.
막는 것은 **전역 `D`·`state`를 60개 함수가 직접 읽는다**는 것이다. 파일을 나누는 순간
그 전역을 어떻게 넘길지 정해야 하고, 그것이 이 작업의 실제 내용이다.

`makePriceChart`가 그 답의 견본이다 — 294줄인데 `(container, D, state)`를 **인자로 받아서**
전역에 손을 대지 않는다. 나머지 함수도 같은 모양으로 바꾸면 파일 경계는 따라온다.

> **이슈로 남기는 이유**: 60개 함수의 시그니처를 바꾸는 일이라 한 PR에 넣으면 리뷰가
> 불가능하고, "동작 무변경"을 증명하기도 어렵다. 위 표의 경계마다 한 단계씩 끊어 여러
> PR로 가야 한다.

#### ㉯ 전역 `D` 하나가 서로 다른 두 스키마를 뜻한다

`load()`가 두 엔드포인트를 부르고 **응답을 같은 변수 `D`에 넣는다**(`:1894`·`:1914`).

| | 주식 (`/api/analyze`) | ETF (`/api/analyze_etf`) |
|---|---|---|
| 이름 | `D.meta.name` | `D.name` |
| 현재가 | `D.meta.price` | `D.price` |
| 판정 | `D.verdict.verdict` — **객체** | `D.verdict` — **문자열** |
| 통화 | `D.meta.currency` | `D.currency` |

`D.verdict`가 어떤 함수에서는 객체이고 어떤 함수에서는 문자열이다. `vTone(v.verdict)`는
객체의 속성을 받고(`:874`), `etfTone(D.verdict)`는 문자열에 `.indexOf('저평가')`를 부른다(`:1486`).
**어떤 함수를 읽고 있는지에 따라 `D`의 뜻이 바뀌고, 파일 안에 그것을 알려 주는 표시가 없다.**

지금 사고가 나지 않는 이유는 `setEtfMode(on)`이 두 뷰를 서로 감추기 때문이다 — 즉
**타입이 아니라 화면 표시 상태가 안전장치 역할을 하고 있다.**

> **이슈로 남기는 이유**: `Dstock`/`Detf`로 갈라 이름을 주는 일 자체는 작지만, ETF 뷰의
> 370줄이 전부 짧은 경로(`D.name`)를 쓰고 있어 손댈 자리가 넓다. ㉮의 분할과 같이 가야 한다.

#### ㉰ 헤더 카드가 두 벌 — 주식과 ETF가 같은 HTML을 따로 적는다

**남은 일 — 이름 세 개를 가른다.** 1번 바구니에서 자사 포함만 고치면 산점도 십자선(11.66×)과
밸류에이션 탭(11.66×)은 맞지만, ①의 재료(9.8×)는 여전히 다르다. 그 차이는 의도된
것(`comparable_peers`의 규모 필터)이니 없앨 것이 아니라 **화면이 구분해 불러야** 한다 —
"업종 중앙"과 "규모 비교가능 피어 중앙"은 다른 값이다. 어느 자리에 어떤 이름을 줄지는
R3(화면 언어)의 판단이 섞이므로 이슈로 남긴다.

무게가 다른 지점이 하나 있다. `src/analysis/bond_math.py`는 **웹 진입점이 아예 임포트하지
않는다** — 임포트하는 곳은 `scripts/check_bond.py`와 Streamlit(`src/ui/pages/bond.py`)뿐이다.
CLAUDE.md는 "실제 실행 진입점은 Meridian 웹(`대시보드실행.bat`)"이라고 적었으니,
**규칙을 지키는 구현은 테스트되고 사용자가 보는 구현은 테스트되지 않는다.**

`serialize.bond_data()`의 독스트링이 "시나리오 계산은 프런트(JS)에서 수행"이라고 밝혀 둔
**의도된 예외**다. 의도를 문제 삼는 게 아니라, 그 예외의 값을 치르고 있다는 것을 적는다.

찾은 반올림 차이 하나는 **도달 불가**로 확인했다. 파이썬 `int(round())`는 0.5를 짝수로,
JS `Math.round()`는 위로 올린다. 그런데 만기는 정수(1·2·3·5·7·10·20·30)이고 이표 주기는
1 또는 2뿐이라(`bond.html:115`) `years × freq`가 반정수가 되는 입력을 **UI로 만들 수 없다**.

#### ㉶ 「현재 PER」도 두 값이다 — 1번 바구니 1번을 고치다 옆에서 나왔다

1번을 고친 뒤 브라우저에서 값을 확인하다 **같은 종류의 어긋남을 하나 더** 찾았다.
이번에는 서버 안에서다(둘 다 payload에 실려 온다).

| 화면 자리 | 출처 | 삼성전자 |
|---|---|---|
| 요약 타일 「PER (TTM)」 · 밸류에이션 탭 「현재」 | `indicators`(`tiles.per`·`multiples[].current`) | **14.52×** |
| 피어표 자사 행 · 산점도 자사 점 | 피어 프레임(`peers.rows[].per`) | **16.73×** |

**밸류에이션 탭의 한 행이 두 정의를 나란히 놓고 비교한다** — 「현재 14.5×」(indicators)와
「업종 중앙값 11.7×」(피어 프레임 중앙값)이다. 그 둘의 비율이 「vs 업종 24% 높음」이라는
**판정 셀**을 만든다. 자사와 피어가 다른 방식으로 계산된 PER이면 그 비교는 기울어져 있다.

두 값이 왜 다른지는 이 라운드에서 판정하지 않았다 — 주가 기준일이 다른지, EPS 기준(연간/TTM)이
다른지, 상장주식수 출처가 다른지를 확인해야 하고 그것은 **R1(데이터 신뢰성)의 방법**이다.
확정한 것은 **한 종목의 PER이 화면에서 두 값으로 존재하고, 그중 하나가 판정에 쓰인다**는 사실이다.

> **이슈로 남기는 이유**: 값의 문제라 구조 판단만으로 못 고친다. 어느 쪽이 맞는지 정하려면
> 원본과 대조해야 한다(R1이 쓴 방법). 다만 **어느 쪽으로 정해도 비교의 양변은 같은 정의를
> 써야 한다**는 것은 정해져 있다.

## 결론

**이 저장소는 좋은 코드를 이미 두 번 써 놓았고, 큰 파일 하나가 그것을 쓰지 않는다.**

R4는 "디자인 시스템은 잘 설계돼 있고 잘 배포되지 않았다"로 끝났다. 코드도 같은 모양이다.
다만 이번에는 **없어서 못 한 것이 아니라, 있는 것을 쓰지 않은 것**이라 진단이 더 분명하다.

- `tiles()`는 지표 타일 스트립을 CSS 클래스로 그리는 옳은 방법이고, `portfolio.js`·`bond.js`에
  **글자 하나까지 같은 두 벌**로 이미 있다. `stock.js`는 같은 물건을 **6번 인라인으로** 적었다.
  그 결과가 R4가 센 "글자 크기 27가지"다.
- `makePriceChart`는 294줄인데 `(container, D, state)`를 인자로 받아 전역에 손대지 않는다.
  분할이 어떻게 생겨야 하는지의 견본이 **이미 같은 파일 안에** 있다. 나머지 60개 함수가
  전역 `D`를 직접 읽는 것이 분할을 막는 실제 원인이고, 빌드 도구의 부재는 아니다
  (브라우저가 ES 모듈을 그대로 읽는다).
- `bond_math.py`는 CLAUDE.md의 규칙("분석은 `src/analysis`의 순수 함수")을 정확히 지킨
  84줄이고, CI가 돌리며, **실제 실행 진입점은 임포트하지 않는다.**

**가장 큰 것은 ㉮(1,990줄)이 맞다.** 다만 이 라운드가 알아낸 것은 그것이 크기 문제가 아니라
**의존 방향 문제**라는 것이다 — 전역을 인자로 바꾸는 작업이 끝나면 파일 경계는 따라온다.
그 다음이 ㉱·㉲(같은 물건을 여러 번 적는 자리)이고, 이 둘이 R4가 넘긴 #74·#73의 **선행
조건**이다. CSS의 73%가 페이지 안에 사는 한 눈금을 만들어도 화면에 닿지 않는다.

**가장 값이 싼 것은 1번 바구니 6~8번이다.** JS에 문법 검사가 없고(`node --check` 한 줄이면
된다), R3·R4·R5가 만든 정적 검증 스크립트 셋이 CI에 걸려 있지 않고, 그중 하나는 문제를
찍고도 종료코드 0을 반환한다. **네 라운드가 만든 회귀 방지 장치가 아무것에도 연결되어
있지 않다** — 사람이 기억해서 돌려야 도는 검증이다. 이것을 먼저 연결해야 앞의 큰 작업이
안전해진다.

**예상하지 못한 것은 구조 문제가 값 문제를 낳고 있었다는 것이다.** 이 라운드는 "읽히는가"만
보기로 했는데, 브라우저에서 도는 계산을 전수로 등록하다가 **화면에 틀린 숫자가 나오는 자리**를
찾았다(1번 바구니 1번). 업종비교 산점도가 자사를 업종 중앙 표본에 넣어서, 삼성전자의 "업종 중앙
ROE" 가로선이 삼성전자 자기 점 위에 그려진다. R1이 값을, R3이 문장을 봤을 때 이것이 안 잡힌
이유는 값도 문장도 틀리지 않았기 때문이다 — **틀린 것은 그 값을 누가 어느 표본으로 계산하느냐**였다.
같은 개념을 두 곳에서 따로 계산하면 조용히 갈라진다는 것이 ㉳가 경고한 실패 방식이고,
그 실패가 이미 일어나 있었다.

**확인하지 못한 것은 "읽힘"이다.** 줄 수·중복 벌 수·인라인 밀도는 다 셌지만, 그 숫자가
낮아지면 정말 읽기 쉬워지는지는 세지 못한다. 잘못 쪼개면 파일 수만 늘고 의존 방향이 꼬여
전보다 나빠질 수 있고, 그 판정은 **사람이 열어서 읽어야** 나온다. R1의 벽은 시간축,
R2는 관측창, R3는 독자, R4는 취향이었다. **R5의 벽은 읽는 사람이다.**
