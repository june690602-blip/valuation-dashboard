# 전반 검토 계획 — 조서(working paper) 방식

이 폴더는 대시보드 전체를 다섯 라운드로 나눠 점검한 **검토 조서**를 담는다.
"무엇을 확인했고, 어떤 근거로, 무엇을 확인하지 못했는지"를 남기는 것이 목적이다.

한 라운드가 끝나면 `R{n}-*.md` 조서 하나가 남는다. 조서는 **다음 라운드의 인계 문서**이기도 하다 —
R2를 시작하는 사람은 R1 조서만 읽으면 되고, R1의 작업 과정을 다시 볼 필요가 없다.

## 왜 나눠서 하나

축마다 "맞다"를 확인하는 방법이 다르다. 섞으면 넷 다 대충 보게 된다.

| 축 | 무엇으로 확인되나 |
|---|---|
| 데이터 신뢰성 | **외부 원본과 대조**해야 알 수 있다 (공시·거래소 값과 비교) |
| 가정의 적합성 | **논거와 민감도**로 따져야 알 수 있다 (이 값을 바꾸면 결론이 뒤집히나) |
| 화면 언어 | 읽어보면 안다 — 판단만 필요 |
| 디자인 | 눈으로 봐야 안다 — 취향이 섞여 대화가 필요 |
| 코드 구조 | 남이 읽어봐야 안다 |

## 순서와 그 이유

**데이터 → 가정 → 화면 언어 → 디자인 → 코드**

- **데이터가 처음**: 데이터가 틀리면 그 위의 모든 것이 정교하게 틀린다.
  이 저장소에 이미 전례가 있다 — `cf78389`(이슈 #35)와 `a70ca59`는 둘 다
  수정종가를 써야 할 곳에 실제 거래가를 쓰거나 그 반대로 써서 **체계적 편향**을 만들었다.
  가정이 아무리 정교해도 이런 건 못 막는다.
- **화면 언어가 가정보다 뒤**: 가정이 바뀌면 그것을 설명하는 문장도 다시 써야 한다.
  문장을 먼저 다듬으면 두 번 쓴다.
- **디자인이 화면 언어보다 뒤**: 문장이 바뀌면 그 문장이 차지하는 자리와 줄 수가 바뀐다.
- **코드가 마지막**: 디자인이 확정돼야 컴포넌트 경계가 정해진다.

## 라운드

| | 라운드 | 답할 질문 | 주 대상 | 조서 |
|---|---|---|---|---|
| R1 | 데이터 신뢰성 | 이 값이 정말 우리가 생각하는 그 값인가 | `src/data/` | `R1-데이터신뢰성.md` |
| R2 | 가정의 적합성 | 이 선택이 정당한가, 바꾸면 결론이 뒤집히나 | `src/analysis/` | `R2-가정적합성.md` |
| R3 | 화면 언어 | 계산 결과를 정확하게, 쉽게 말하는가 | `web/*.html`, `web/assets/*.js` | `R3-화면언어.md` |
| R4 | 디자인 일관성 | 한 사람이 만든 것처럼 보이는가 | `web/assets/meridian.css` + 전 화면 | `R4-디자인일관성.md` |
| R5 | 코드 구조 | 남이 열어서 읽을 수 있는가 | 전체 (특히 `web/assets/stock.js`) | `R5-코드구조.md` |

## 발견을 담는 세 바구니

각 조서는 발견을 다음 셋으로 나눈다. **분류 자체가 결론**이다.

1. **지금 고침** — 명백한 오류. 이 라운드에서 PR로 처리한다.
2. **이슈로 남김** — 고쳐야 하지만 범위가 커서 별도 작업이 필요하다. GitHub 이슈를 만들고 번호를 적는다.
3. **한계로 문서화** — 무료 공개 데이터로는 고칠 수 없다. **왜 못 하는지**를 적는다.

3번이 가장 중요하다. 예를 들어 "지난 5년간 저평가 종목들의 실제 수익률"은
과거 시점 상장 목록이 없어 **생존편향**을, 시점별 재무제표 빈티지가 없어 **룩어헤드**를
피할 수 없다. 억지로 만든 그럴듯한 수익률보다, 왜 만들지 않았는지를 아는 편이 정확하다.

## 진행 규칙

- **한 라운드 = 한 세션.** 이전 라운드의 대화를 끌고 가지 않는다. 인계는 조서로 한다.
- **범위를 파일 목록으로 못 박고 시작.** "`src/data` 전부"가 아니라 파일 이름을 적는다.
- **검증은 대화가 아니라 스크립트로.** `scripts/`에 재현 가능한 검증 스크립트를 만들고
  그 출력을 근거로 삼는다. 감사에서 재현 가능성이 핵심이고, 스크립트 자체가 산출물이 된다.
  기존 `scripts/check_analysis.py`·`scripts/check_backtest.py` 패턴을 따른다.
- **발견과 수정을 분리.** 라운드 중에는 조서에 적기만 하고, 수정은 그 라운드 끝에 모아서 한다.
- **이슈에는 「어디를 손대야 하나」를 반드시 적는다.** 이 검토가 만드는 이슈는 몇 달 뒤에,
  또는 다른 사람이 집는다. 문제만 적힌 이슈는 집는 사람이 파일을 찾는 데서 시간을 다 쓴다.
  다음 넷을 표로 남긴다 — **고쳐야 하는 곳**(파일·함수·무엇을) / **같이 움직이는 곳**(여기를
  고치면 함께 봐야 하는 곳) / **손대면 안 되는 곳**(지금이 맞는 곳) / **확인 방법**(검증
  명령과 합격 기준). 줄 번호는 밀리므로 기준 커밋을 밝히고 함수 이름을 함께 적는다.
  기존 이슈 #56·#57·#58·#62·#63이 이 형식이다.
- 브랜치·PR은 `CLAUDE.md`의 「브랜치 · PR 규칙」을 따른다 — 항상 최신 `main`에서 분기, base는 `main`.
