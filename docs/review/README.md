  종합 적정가의 **76%가 "자기 5년 PER 중앙값"이라는 한 숫자**에 매달려 있다.
- **R3** — PR #47이 세운 원칙이 **그 PR이 손댄 자리에만** 적용돼 있었다.
- **R4** — 디자인 시스템은 잘 설계돼 있고 **잘 배포되지 않았다.** 홈에서 주식으로 넘어가는
  한 번의 클릭에서 로고가 사라지고 지면이 미색에서 순백으로 바뀌었다.

  **누가 어느 표본으로 계산하느냐**가 틀렸기 때문이다.

## 검증 스크립트

각 라운드는 **재현 가능한 검증 스크립트**를 남겼다. 감사에서 재현 가능성이 핵심이고,
스크립트 자체가 산출물이 된다. 각 점검은 `[확인]` / `[문제]` / `[불가]` 중 하나로 결론 낸다 —
**`[불가]`가 3번 바구니(한계) 후보**다.

### CI가 PR마다 자동으로 도는 것

네트워크·API 키가 필요 없어 `.github/workflows/quality.yml`에 걸려 있다.

```bash
python scripts/check_screen_language.py   # R3 — 판정 어휘·층위 (관문)
python scripts/check_design.py            # R4 — 토큰·셸·대비 (기준선 관문)
python scripts/check_structure.py         # R5 — 파일 크기·중복·계산 경계 (기준선 관문)
```

뒤 둘은 **`KNOWN_OPEN` 기준선 방식**이다. 지금 열려 있는 이슈의 문제 건수를 스크립트에 적어
두고 **그보다 늘어날 때만** 실패한다. 열린 이슈까지 실패로 처리하면 CI가 늘 빨간 상태가 되어
아무도 보지 않게 되기 때문이다. **이슈를 닫을 때 `KNOWN_OPEN`을 함께 내리는 것이 그 이슈의
완료 조건**이다.

### 손으로 돌리는 것 (네트워크·키 필요)

```bash
python scripts/check_data_integrity.py     # R1 — 원본 대조 (--static은 네트워크 없이 됨)
python scripts/check_sensitivity.py        # R2 — 가정을 흔들어 판정이 뒤집히는지
python scripts/check_analysis.py KR 005930 # 분석 엔진 헤드리스 확인
python scripts/check_backtest.py KR 005930
python scripts/check_etf.py US SPY
```

### 레지스트리 — 새로 만들면 등록해야 통과한다

검증의 핵심 장치다. 각 스크립트가 "지금 이 저장소가 어떤 상태인지"를 표로 들고 있고,
등록된 값과 실제가 어긋나면 `[문제]`로 떨어진다.

| 스크립트 | 레지스트리 | 무엇을 못 박나 |
|---|---|---|
| R1 | `PRICE_LEVEL_SITES` · `TOTAL_RETURN_SITES` | 어느 함수가 실거래가를, 어느 함수가 수정종가를 쓰는가 |
| R3 | `LAYER_SITES` | 어느 자리에서 판정 어휘를 쓰고 어느 자리에서 관찰 어휘를 쓰는가 |
| R4 | `SHELL_SITES` · `VERDICT_COLOR_SITES` · `TEXT_TOKENS` | 화면 7장의 헤더 구현 · 판정 색 · 텍스트 토큰 대비 |
| R5 | `SIZE_BUDGET` · `SHARED_HELPERS` · `CLIENT_MATH` | 파일 줄 수 상한 · 공용 헬퍼 벌 수 · **브라우저에서 도는 금융 수식** |

`SIZE_BUDGET`과 `INLINE_BUDGET`은 **내려가기만 한다.** 파일을 쪼개면 예산도 같이 내려 적어야
다음 사람이 다시 부풀릴 수 없다.

**이 규칙이 실제로 작동한 사례가 있다.** R5 직후 PR #87(모바일 화면 깨짐)이 폰에서 5px로
렌더되던 적정가 차트를 고치며 `stock.js`가 78줄 늘어 상한을 넘겼고 CI가 실패했다. 예산을
올려 적는 대신 **PR #90이 주가 캔버스 차트 294줄을 `stock-price-chart.js`로 떼어냈다**
(2,086 → 1,795줄, 예산도 1,800으로 내려 적음). 상한이 파일을 쪼개게 만든 것이다 —
#79의 1단계가 이렇게 시작됐다.

## 방법 — 왜 이렇게 했나

### 왜 나눠서 하나

축마다 "맞다"를 확인하는 방법이 다르다. 섞으면 넷 다 대충 보게 된다.

| 축 | 무엇으로 확인되나 |
|---|---|
| 데이터 신뢰성 | **외부 원본과 대조**해야 알 수 있다 (공시·거래소 값과 비교) |
| 가정의 적합성 | **논거와 민감도**로 따져야 알 수 있다 (이 값을 바꾸면 결론이 뒤집히나) |
| 화면 언어 | 읽어보면 안다 — 판단만 필요 |
| 디자인 | 눈으로 봐야 안다 — 취향이 섞여 대화가 필요 |
| 코드 구조 | 남이 읽어봐야 안다 |

### 순서와 그 이유

**데이터 → 가정 → 화면 언어 → 디자인 → 코드**

- **데이터가 처음**: 데이터가 틀리면 그 위의 모든 것이 정교하게 틀린다.
  이 저장소에 이미 전례가 있다 — `cf78389`(이슈 #35)와 `a70ca59`는 둘 다
  수정종가를 써야 할 곳에 실제 거래가를 쓰거나 그 반대로 써서 **체계적 편향**을 만들었다.
  가정이 아무리 정교해도 이런 건 못 막는다.
- **화면 언어가 가정보다 뒤**: 가정이 바뀌면 그것을 설명하는 문장도 다시 써야 한다.
  문장을 먼저 다듬으면 두 번 쓴다.
- **디자인이 화면 언어보다 뒤**: 문장이 바뀌면 그 문장이 차지하는 자리와 줄 수가 바뀐다.
- **코드가 마지막**: 디자인이 확정돼야 컴포넌트 경계가 정해진다.

**이 순서는 실제로 값을 했다.** R5가 코드 구조를 보다 찾은 값의 결함 둘은, 값(R1)이나
문장(R3)의 렌즈로는 보이지 않는 것이었다 — 값도 문장도 틀리지 않았고 **누가 어느 표본으로
계산하느냐**가 틀렸기 때문이다.

### 발견을 담는 세 바구니

각 조서는 발견을 다음 셋으로 나눈다. **분류 자체가 결론이다.**

1. **지금 고침** — 명백한 오류. 그 라운드에서 PR로 처리한다.
2. **이슈로 남김** — 고쳐야 하지만 범위가 커서 별도 작업이 필요하다. GitHub 이슈를 만들고 번호를 적는다.
3. **한계로 문서화** — 무료 공개 데이터나 이 방법으로는 확인할 수 없다. **왜 못 하는지**를 적는다.

3번이 가장 중요하다. 위의 「각 라운드가 만난 벽」이 그것이다.

### 진행 규칙

- **한 라운드 = 한 세션.** 이전 라운드의 대화를 끌고 가지 않는다. 인계는 조서로 한다.
- **범위를 파일 목록으로 못 박고 시작.** "`src/data` 전부"가 아니라 파일 이름을 적는다.
- **검증은 대화가 아니라 스크립트로.** 위의 「검증 스크립트」가 그 산출물이다.
- **발견과 수정을 분리.** 라운드 중에는 조서에 적기만 하고, 수정은 그 라운드 끝에 모아서 한다.
- **취향이 섞이는 것은 혼자 정하지 않는다.** R4가 이 방식을 썼다 — 발견까지만 확정하고
  방향은 선택지를 붙여 열어 둔 뒤, 대화로 정하고 그 근거를 조서에 적었다.
- **이슈에는 「어디를 손대야 하나」를 반드시 적는다.** 이 검토가 만드는 이슈는 몇 달 뒤에,
  또는 다른 사람이 집는다. 문제만 적힌 이슈는 집는 사람이 파일을 찾는 데서 시간을 다 쓴다.
  다음 넷을 표로 남긴다 — **고쳐야 하는 곳**(파일·함수·무엇을) / **같이 움직이는 곳** /
