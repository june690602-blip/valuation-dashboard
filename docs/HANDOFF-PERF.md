## 한 줄 요약

**계산은 0.04초다. 나머지 13초는 전부 서로 독립인 네트워크 호출을 한 줄로 세워 둔 것이다.**

## 1. 실측 — 캐시 상태에 따라 병목이 **바뀐다**

세 번 쟀고 셋 다 그림이 다르다. **한 종목만 재고 결론짓지 마라.**

| 단계 | 005930 (완전 warm) | 005930 (뉴스 warm) | 161890 (cold) |
|---|---|---|---|
| **총** | **3.56s** | **7.94s** | **13.2s** |
| Gemini 업종분류 | 0.01 (캐시) | ~0 (캐시) | **4.04** |
| DART 재무 | 0.52 | 0.87 | **2.49** |
| 뉴스 3건 | 0.02 (캐시) | **3.73** | **2.38** |
| yfinance 재무제표 | **1.72** | 1.46 | 1.82 |
| yfinance TTM | **1.11** | 1.63 | 1.33 |
| 기업개요·주가·지수 | 0.1 | 0.2 | 0.71 |
| **순수 계산 전부** | **0.06** | **0.04** | **0.04** |

**읽는 법** — 캐시가 차면 **yfinance 재무·TTM**이, 뉴스 캐시가 끊기면 **뉴스**가,
새 종목이면 **Gemini**가 바닥이다. **한 곳만 고치면 안 된다.** 셋 다 병렬 그룹에 넣어야
어느 상태에서든 줄어든다.

> ⚠ 위 표를 그대로 인용하지 마라 — 캐시·시간대·Yahoo 상태에 따라 매번 다르다.
> **`check_load_timing.py`를 직접 돌려 그때의 표를 내라.** 이 문서가 주장하는 것은
> 숫자가 아니라 **모양**이다: 계산 ≈ 0, 나머지는 순차 I/O.

## 2. 무엇이 순차인가

### ㉠ 뉴스가 파이프라인 **뒤**에 선다

`serialize.analyze()`는 `_pipeline`(전체 로드+계산)을 끝낸 **다음** `_news(d)`를 부른다.
그런데 뉴스가 실제로 쓰는 것은 `d.name` · `d.market` · `d.yahoo_ticker` · `d.sector`뿐이고,
그 넷은 `resolve()`(상장목록 조회, 0.01초)만 하면 전부 나온다.

### ㉡ `load()` 안이 전부 순차

`kr_provider.load()`가 부르는 순서다. **화살표가 진짜 의존인 것은 셋뿐이다.**

```
resolve → yfinance재무 → DART → 시세 → (주식수) → TTM → 네이버 → 지수
        → Gemini업종분류 → 피어목록 → build_peer_table(여기만 이미 병렬)
```

진짜 의존:
- 시세 → `price` → `mcap = shares × price`
- `shares`(대개 KRX 상장목록에서 즉시) → `extract_ttm(tk, shares)`
- Gemini 업종분류 → `peer_codes` → `build_peer_table`

**나머지는 전부 서로 모른다.**

### ㉢ 뉴스 안의 3회도 순차

`_gather_news_items`가 기업·산업·거시 헤드라인을 **차례로** 받는다(`_google_news` 3회).

## 3. 단계

### 1단계 — 측정 하네스 ✅ **끝남**

`scripts/check_load_timing.py`가 이 PR에 있다. **먼저 돌려 지금 표를 뜨고 시작해라.**

### 2단계 — 뉴스를 파이프라인과 나란히 ✅ **끝남** (실측 5.68s → 2.98s)

- `_gather_news_items(d)` → `(name, market, ticker, sector)`로 인자를 낮춘다
- `analyze()`가 `resolve()`만 먼저 하고 **뉴스와 `_pipeline`을 동시에** 띄운다
- **2b**: `_google_news` 3회도 스레드풀로 (3.7s → 1.9s)

> ⚠ **행동이 바뀌는 유일한 지점이다.** 산업 뉴스 질의에 쓰는 업종이 *AI 분류 후*가 아니라
> *KRX/GICS 원본*이 된다. 종목에 따라 산업 헤드라인이 달라진다. 오히려 안정적이라고 보지만
> **골든 테스트가 여기서 걸릴 것이므로 미리 알고 있어라.**

### 3단계 — provider 로드 경로 병렬화 ✅ **끝남** (KR 일곱 · US는 info 먼저)

`KRProvider.load` / `USProvider.load`에서 독립인 것들을 한 그룹으로:

```
동시 (워커 4):
  yfinance재무 · DART · TTM · 시세프레임 · 지수 · 네이버지표 · Gemini업종분류
      ↓ 조인
  가격·시총 확정 → 재무 병합 → 피어목록 → build_peer_table(기존 8워커)
```

**핵심 관찰**: `extract_ttm(tk, shares)`의 `shares`는 KRX 상장목록에서 바로 나온다
(`tk.info` 폴백은 드물다). 그래서 TTM도 같이 띄울 수 있다 — 이걸 놓치면 병렬 그룹이 반쪽이 된다.

### 4단계 — 진행 표시를 스레드에 넘긴다 ✅ **끝남** (`progress.bind_reporter`)

**`progress.py`는 `threading.local()`이다.** 지금 `build_peer_table`이 동작하는 건
`report()`를 **메인 스레드에서만** 부르기 때문이다(워커는 `fetch_info_metrics`만 돈다).
3단계로 옮기면 **조용해진다.**

→ 부모의 콜백을 워커에 심는 헬퍼를 `progress.py`에 추가하고, 병렬 그룹에 `자료 수집 n/7`
단계를 붙인다.

### 5단계 — ADR-0045 + 검증 ✅ **끝남**

[ADR-0045](adr/0045-parallelize-the-load-path.md) · `tests/test_load_parallel.py`(19건, Red-Green
확인) · `scripts/check_payload_parity.py`(합격선). 화면 수집 카드 첫 줄에 `자료 수집 n/7`이 붙는다.

## 4. 함정 — 코드를 읽어야만 알 수 있는 것들

| | |
|---|---|
| **`progress.py`가 thread-local** | 워커에서 진행 표시가 침묵한다. 4단계가 이것 하나를 위해 있다 |
| **`warnings` 순서가 비결정적이 된다** | 지금은 `load()`가 순서대로 `warnings += w` 한다. 병렬로 하면 순서가 매번 달라져 **화면 문구 순서가 흔들린다.** 태스크별 리스트로 받아 **고정 순서로 이어붙여라** |
| **`yf.Ticker`를 두 스레드가 공유** | `extract_financials(tk)`와 `extract_ttm(tk, …)`가 지금 같은 객체를 쓴다. yfinance는 스레드 안전이 보장되지 않는다 — **태스크마다 자기 `Ticker`를 만들어라**(생성 비용 0) |
| **예외의 의미가 태스크마다 다르다** | US는 시세 실패가 **치명**(ValueError로 중단), KR의 미조정 시세 실패는 **경고**다. 퓨처로 바꾸면 전부 `.result()`에서 같은 모양으로 올라온다 — **치명/경고를 명시적으로 분류해라** |
| **`file_cache`는 안전하다** | 키 단위 락이 있어 다른 키는 동시에, 같은 키는 한 번만 만든다. `build_peer_table` 도크스트링이 이미 그 근거를 적어 뒀다 |
| **yfinance 레이트리밋** | 평상시 성공률 62%다(`cache.py` 주석). 새 풀은 **4워커로 제한**하고, 피어 8워커와 시간대가 겹치지 않게 둬라(피어는 조인 뒤라 자연히 안 겹친다) |
| **인라인 스타일 예산** | 화면을 건드리면 `check_structure.py`가 본다. 이 작업은 화면을 안 건드릴 것이다 |

## 5. 합격선 — **"아무것도 안 바뀌었음"을 증명하는 쪽이 어렵다**

빨라지는 것은 쉽다. 어려운 것은 **출력이 같다**는 증명이다.

```
골든 테스트: 픽스처로 analyze() 페이로드를 병렬화 전후 완전 일치 비교
             (정상 경로 + 실패 경로 둘 다 — 예외 의미가 바뀌는 것이 진짜 위험이다)
병렬성 테스트: 각 fetch가 0.2초 자는 가짜 provider로 총 시간 < 순차 합
회귀:        pytest tests/ · python scripts/check_all.py (관문 11)
실측:        python scripts/check_load_timing.py KR 005930 / KR 161890 / US AAPL
실화면:      진행 표시가 계속 도는지 · 콘솔 에러 0
```

**골든 픽스처를 먼저 떠라.** 병렬화를 하고 나서 뜨면 무엇과 비교하는지가 사라진다.

## 6. 범위 밖 — 하려면 **물어라**

**Gemini 4초를 화면 밖으로 미루기**(판정 먼저 그리고 업종 비교 탭만 늦게 채우기).
체감 2초대까지 가지만 **첫 화면의 ① 업종 상대가치가 잠깐 비어 있다가 값이 채워진다.**
판정 가중의 38.5%가 ①에 걸려 있으므로 **판정 숫자가 나중에 한 번 바뀌는 화면**이 된다.

이건 성능 문제가 아니라 *"판단 근거를 보여주되 단정하지 않는다"*는 이 도구의 성격 문제다.
**혼자 정하지 마라.**

## 7. 이번에 보고도 손대지 않은 것

**`_pipeline`이 `@lru_cache`라 동시 같은 종목 요청이 중복 실행된다.**
`server.cached_analyze`는 `_LOCK`을 잡았다가 **풀고 나서** `analyze()`를 부른다. 그래서
같은 종목을 두 사람이 동시에 조회하면 전체 수집이 두 벌 돈다. PR #151이 `file_cache`에
single-flight를 넣었지만 `_pipeline` 자체는 그대로다.

병렬화하다 이 자리를 반드시 마주친다. **이 인계문의 범위가 아니고, 고칠 거면 별도로 재고
별도 PR로 해라** — 여기 섞으면 "출력이 안 바뀌었나"를 판단할 수 없게 된다.

## 8. 재지 않은 것

- **완전 cold 상태**(피어 info 캐시까지 비었을 때). `build_peer_table` 도크스트링이
  *"순차 30초대 → 병렬 6~8초대"*라고 적어 뒀으므로 그 경우 피어가 바닥이 되고, 피어는
  **Gemini 업종분류 뒤에 와야 해서** 이번 병렬화로 줄지 않는다. 줄이려면 KRX 폴백 피어를
  먼저 투기적으로 받아 두는 별도 설계가 필요하다.
- **서버 부하 상태에서의 동작.** 혼자 돌릴 때만 쟀다.
- **US의 cold 경로.** KR만 세 번 쟀고 US는 한 번도 안 쟀다.
